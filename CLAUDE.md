# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MoneyBook is an independent personal finance app for Android: entries, accounts and cards, budgets, stats, repeats, multi-currency, photos, passcode, widgets, and import/export of the Money Manager (Realbyte) Excel format. It has an optional self-hosted Kotlin/Ktor + Postgres sync and backup server (`server/`, `deploy/`), run in Docker and reached over HTTPS, for example through Tailscale. The app side of the sync (opt-in login, offline-first, merge or replace) is in `android/`. It is not affiliated with Realbyte.

- `docs/superpowers/` (design specs, plans) and `docs/ui-spec.md` (measured layout notes) are local-only developer notes and are not in the repository (gitignored). If you have them, the design spec defines milestones M0–M4.
- Execution progress and deviations ("Ruling:" lines) of a plan are in `.superpowers/sdd/<plan-name>/progress.md`, which is gitignored. Read it before resuming a plan.

## Toolchain and commands

Every shell must start with `source ~/android-toolchain/env.sh`, which provides JDK 17, `ANDROID_HOME` and adb. Run these through bash/zsh (not fish). `env.sh` does not put the emulator on PATH, so use `$ANDROID_HOME/emulator/emulator -avd <avd name>`.

There are three independent Gradle builds (`shared`, `android`, `server`), each with its own wrapper (Gradle 9.8.0, checksum-pinned). There is no root build.

```bash
cd shared  && ./gradlew test                                   # pure Kotlin/JVM library
cd server  && ./gradlew test                                   # Ktor server; needs a Docker daemon (Testcontainers starts postgres:17-alpine per test class)
cd android && ./gradlew :app:testDebugUnitTest                 # JVM + Robolectric tests (no device needed)
cd android && ./gradlew :app:testDebugUnitTest --tests 'com.moneybook.ui.edit.EditTxnViewModelTest'
cd android && ./gradlew :app:testDebugUnitTest --tests '*AggregationsTest.monthly*'
cd android && ./gradlew :app:assembleDebug                     # or :app:installDebug with ANDROID_SERIAL set
```

- CI/release: `.github/workflows/android.yml` runs the shared tests, and on `v*` tags the android unit tests, then `:app:assembleRelease`. `android/app/build.gradle.kts` signs the release build only when `MB_KEYSTORE_FILE` (+ `MB_KEYSTORE_PASSWORD`, `MB_KEY_ALIAS`, `MB_KEY_PASSWORD`) is set; `MB_VERSION_CODE`/`MB_VERSION_NAME` set the version. The workflow reads the key from the secrets `MB_KEYSTORE_BASE64`, `MB_KEYSTORE_PASSWORD`, `MB_KEY_ALIAS`, `MB_KEY_PASSWORD`; without them it builds an unsigned APK. Never commit a keystore.
- `.superpowers/sdd/run.sh shared|android|server <gradle args>` runs a build and prints only errors and the test counts (`.superpowers/sdd/both.sh` runs shared and android).
- Server build and deploy (`deploy/README.md` has the full steps):
  - `cd server && ./gradlew installDist` builds the distribution; the image is built from the repo root with `docker build -f server/Dockerfile .`.
  - `cd deploy && cp .env.example .env` (gitignored; fill it), `mkdir -m 700 backups`, `docker compose up -d --build` (with `sudo` if your user is not in the `docker` group); put `MB_API_KEY` (`openssl rand -hex 32`) in `.env`, the app takes the same key.
  - `docker compose exec backup sh /backup/backup.sh now` runs a backup; `./restore.sh backups/daily/moneybook-<date>.dump [backups/daily/attachments-<date>.tgz] [--yes]` restores one.
  - For a test run on one machine set `MB_HOST_PORT` to a free port and `COMPOSE_PROJECT_NAME`/`COMPOSE_ENV_FILES` to a throwaway project and env file, so nothing real is touched; `down -v` afterwards.
- Opt-in smoke tests on your own files (never committed): `cd shared && MB_REAL_EXPORT=<path to a Money Manager xlsx export> ./gradlew test --rerun-tasks -i | grep "real export:"`; `MB_LEGACY_EXPORT=<path to a legacy xlsx>` likewise (grep `legacy export:`).
- Devices: an Android 14 (API 34) x86_64 emulator at 1080×2400, 420 dpi, and a physical phone. Debug builds reach a Docker server on the desktop at `http://10.0.2.2:<port>` from an emulator: `src/debug/res/xml/network_security_config.xml` (debug manifest overlay) allows cleartext to `10.0.2.2` and `localhost` only, release allows none. The manifest has `INTERNET`. With several devices attached set `ANDROID_SERIAL`. Font sizes in `ui/theme/Type.kt` are calibrated on a physical phone.
- `tools/fetch_icons.py` regenerates `res/drawable/ic_*.xml` from Material Symbols Outlined, weight 300.
- `tools/adb_ui.py <serial> text "More" text "Backup" shot backup` drives the app by on-screen text (tap, back, list, screenshots into gitignored `reference/shots/`).
- `tools/measure.py` and `tools/rows.py` measure text boxes and divider rows in two screenshots, for calibration.
- `tools/planblock.py <plan> <marker> [out]` copies a code block out of a plan when executing it, instead of retyping.

## Architecture

- **`shared/`** (`com.moneybook.shared`) has no Android dependencies, so the future server can reuse it. It holds:
  - the model enums;
  - `MoneyFormat`/`CurrencySpec`, which format Realbyte-style (`525.00Kč`) from Long minor units (stored in ISO decimals; `display` is the Decimal point setting);
  - `RealbyteCurrencies` (Realbyte's 123 currencies with their default symbol and position) and `Fx` (rates as "1 sub = rate main", `BigDecimal`, half up to the target's decimals);
  - `XlsxReader`, a SAX-based first-sheet reader. It spools the input to an owner-only temp file and uses `ZipFile`, because Realbyte's zips have zero-size data descriptors that `ZipInputStream` rejects;
  - `RealbyteExcelImporter`, which turns rows into an `ImportBatch` with deterministic `sourceKey`s so re-imports are idempotent (both importers skip only live entries, so a re-import after a reset, or of an entry deleted by hand, brings it back);
  - `XlsxWriter` (one sheet: inline strings, plain decimals, one date style) and `RealbyteExcelExporter`, which writes Realbyte's column layout (a transfer is a Transfer-Out plus a Transfer-In row) so the importer reads the export back;
  - `LegacyExcelImporter` for the old app's `Date | Income/Expenses | Category | Memo | Amount` sheet, and `CategoryMatcher`, which suggests an existing category for an imported name;
  - `dto/`: `@Serializable` DTOs of every entity (without `dirty`/`serverVersion`), for backups now and the M3/M4 sync later;
  - `BackupCodec`: a backup is a zip whose `backup.json` holds a `BackupDto`; `read` checks the format, version and every reference before returning.
  - `sync/` (`SyncEntity`, `SyncChange`/`SyncRequest`/`SyncResponse`, `LoginRequest`/`RefreshRequest`/`TokenResponse`, the size limits): the wire types of the sync protocol. `SyncEntity.validate(change)` decodes a payload into its DTO (unknown keys ignored) and checks the id (`currency` uses its `code`, `settings` is the single row `app`, an attachment's `fileName` is `[0-9a-f]{32}.jpg`); it never echoes input in its messages. `overwriteEnvelope` makes a payload's `updatedAt`/`deleted` agree with the envelope's.
- **`server/`** (`com.moneybook.server`, Ktor 3 on Netty, plain JDBC + HikariCP + Flyway `V1__init.sql`, `V2__server_meta.sql` and `V3__api_key.sql`, no ORM) consumes `shared` via `includeBuild("../shared")`. `Main.kt` `module(config, ds, clock)` wires everything; `Config` reads `MB_DB_URL`, `MB_DB_USER`, `MB_DB_PASSWORD`, `MB_JWT_SECRET` (at least 32 bytes), `MB_API_KEY` (at least 32 characters), `MB_DATA`, `MB_PORT`. `inTransaction` is blocking, so routes call it inside `withContext(Dispatchers.IO)`. Hikari runs READ_COMMITTED. `SyncResponse.epoch` (from `server_meta`) changes whenever `restore.sh` restores a dump; the M4 client must then reset its cursor to 0 and re-push every row. U+0000 is rejected everywhere it could reach SQL (it would be a 500 and a poisoned batch). Attachment PUT checks the MD5 against the name, and `/v1/auth/*` bodies are capped at 64 KiB.
  - **Auth** (`Auth.kt`, `Jwt.kt`, `Users.kt`): single-user, no signup, no passwords. `POST /v1/auth/login|refresh|logout`. Login takes `{apiKey, deviceId, deviceName}` and compares `sha256(apiKey)` to the digest of `MB_API_KEY` with `MessageDigest.isEqual` (a wrong key is 401 `invalid_key`), then issues tokens for the owner. The owner is the oldest user (`created_at`; an older deployment keeps its user and data) or, on an empty `app_user`, a new one named `owner` (`password_hash` is nullable since V3); `prepareAuth` runs this at startup (`main()`, and the tests' `withApp`). **Key rotation:** V3 adds `server_meta.key_hash` (hex sha256 of the key); at startup a stored hash that differs from the current key's deletes every refresh token (each device must log in with the new key), then the new hash is stored. The key itself is never stored or logged. A 15-minute HS256 access token with `sub` (user id) and `did` (device id), a 90-day refresh token stored as sha256 only and rotated on each use; presenting a used one revokes the device's live tokens. Login is rate-limited (10 per minute, one global bucket). Routes get the user and device only from the token (`principalIds()`), never from body, query or path, and every query filters by user id. Access tokens are not checked against the database, so a logout or a key change takes effect when the token expires.
  - **Sync** (`Sync.kt`): one endpoint, `POST /v1/sync {cursor, changes[]}`, push then pull in one transaction. It first takes `pg_advisory_xact_lock` on the user, so versions commit in order and a pull never skips a row. Validation (at most 1000 changes, payload at most 64 KiB, body at most 16 MiB, `SyncEntity.validate`) rejects the whole request with a 400. An `updatedAt` more than 5 minutes ahead is clamped to server time. Each change is a last-write-wins upsert on `(updatedAt, deviceId)` with `deviceId` compared `collate "C"`; a change that loses (older, or the same change sent again) is rejected and the winning server row is added to the response. The pull returns rows with `version > cursor` (a global sequence) in pages of 1000 with `hasMore`. Tombstones are kept forever. The body is decoded from bytes with the server's own `Json`, because `ContentNegotiation` turns an oversized chunked body into a 400.
  - **Attachments** (`Attachments.kt`): `PUT|GET|HEAD /v1/attachments/{fileName}` (`[0-9a-f]{32}.jpg`), stored at `$MB_DATA/attachments/<userId>/<name>`, written to a temp file, fsynced and moved atomically. 201 created, 204 when the name exists, 413 above 16 MiB (counted while streaming). Files of tombstoned attachments are not deleted yet.
  - `GET /health` answers `select 1`; errors are `{"error":"<code>"}`; `CallLogging` logs only method, path and status. Tests extend `testutil/PostgresTestBase` (a container per class, tables truncated per test) and use `withApp { client -> }`.
- **`deploy/`** (`docker-compose.yml`, `.env.example`, `backup/backup.sh`, `restore.sh`, `README.md`): three services, `db` (postgres:17-alpine, no published port), `api` (built from `server/Dockerfile`, non-root uid 1000, volume `data`) and `backup`. Only `api` publishes a port, `127.0.0.1:${MB_HOST_PORT:-8095}:8080`; HTTPS comes from the Tailscale already running on the host, not from a sidecar. Any Docker host works (a home server, a CasaOS box): after enabling MagicDNS and HTTPS certificates in the Tailscale admin console, `tailscale serve --bg --https=443 http://127.0.0.1:8095` (`--https=8443` if 443 is taken; `sudo docker exec tailscale ...` when Tailscale runs in a container) gives `https://<machine name>.<tailnet>.ts.net`, which the app uses as its server URL (so the phone needs Tailscale on, even at home). There is no plain HTTP on the LAN. `backup.sh` dumps at 03:00 (container `TZ`) into `deploy/backups/`: `pg_dump -Fc` plus a tarball of the attachments, owner-only, 7 daily, 4 weekly (Sunday), 6 monthly (1st); a failed run deletes nothing. `restore.sh` validates the files, stops `api`, drops and recreates the database, restores it, swaps the attachments through `docker compose run` and starts `api`. M3 was accepted on one machine (login on two devices, push/pull, attachment, backup, drop, restore, identical pull).
- **`android/`** is one module, `:app`. It consumes `shared` via `includeBuild("../shared")` as `com.moneybook:shared`.
  - AGP 9 with built-in Kotlin, KSP and Room. compileSdk is **37** (current AndroidX requires it); targetSdk 36, minSdk 26.
  - **Data** (`data/`): Room is the source of truth.
    - Every entity has sync columns (`updatedAt`, `deleted` tombstone, `dirty`, `serverVersion`) for the M4 sync.
    - Deletes are soft (tombstones). Accounts and groups are different: deleting one never touches its entries (see M2k below).
    - Balances are never stored; `AccountDao.observeBalances(until)` computes them in SQL.
    - Date-times are fixed-width local text (`DbTime`), so range queries compare strings.
    - Default groups, accounts and categories use deterministic `default-*` ids.
    - M2c added the `memo` (Trans → Note) and `bookmark` tables. The database is at version 2; `MoneyBookDatabase.MIGRATION_1_2` creates both, and `MigrationTest` builds a version 1 file from `schemas/…/1.json` and opens it at version 2.
    - The backup format is version 2: it adds memos, bookmarks and the autocomplete settings (`AppSettings.autocomplete`, `autocompleteSince`). Version 1 files still restore, with no memos or bookmarks.
    - M2d added the `repeat_rule` table (repeats and monthly installment plans). The database is at version 3; `MIGRATION_2_3` creates it, and `MigrationTest` also opens a version 2 file from `2.json` at version 3.
    - `RepeatRepository.catchUp(today)` adds every occurrence that has come due ("On the date") as an ordinary entry with the derived id `rep-<ruleId>-<date>`, skipping ids that exist even as tombstones, so it can run any number of times. It runs on app start, on every foreground (`MainActivity.onStart`) and after a rule is saved. The occurrences are stamped `updatedAt` 0 (like seeds) and the rule keeps its `updatedAt` (the monotonic trigger lifts it to old + 1), because a device that has not synced yet must not overwrite another device's edit, tombstone or rule delete; any real edit wins and two devices adding the same occurrence tie on identical content. A rule waits while its account is hidden or not ACTIVE (or its group is not ACTIVE) or its category deleted.
    - The backup format is version 3: it adds the repeat rules. Older files restore with none.
    - M2e Configuration options live in `AppSettings` (start screen, monthly start date with its weekend rule, week start, swipe, color set, time input, show description, input order, note button, style), stored by name in DataStore. All are backed up except `style`, which is a device setting: a restore keeps it.
    - M2f added the device-only `DeviceSettings` (passcode hash and salt, alarm on and time, quick add) in their own `device_settings` DataStore (`DeviceSettingsRepository`). They are never in backups, resets or `AppSettings`, and `res/xml/data_extraction_rules.xml`/`backup_rules.xml` keep that file out of Android's own backup too.
    - M2l added `DeviceSettings.biometric` (default on) and `lockDelaySeconds` (Request Passcode: 0, 60, 300, 900, 3600; `LockDelay`), device-only.
    - M2g added `DeviceSettings.widgetBackground` (a `StyleMode`) and `widgetOpacity` (0–100), Widget Settings' look for the summary widgets; device-only like the rest.
    - M2h cards use the account columns that existed since version 1: `statementDay` (Settlement Date), `paymentDay` and `paymentAccountId` (Pay's From); a card without days uses 1 and 1. `autoPay` stays unused (Realbyte 4.12.13 has none). `AccountBalanceRow` carries them, and `AccountDao.observeCardCharges()` returns every card's expenses and transfers out. `AppSettings.cardExpenseMode` (More → Accounts → Card expenses display config) is synced and backed up (`SettingsDto.cardExpenseMode`, default `AT_THE_TIME`).
    - M2i (currencies) put the database at version 4. `MIGRATION_3_4` adds the `currency` table (display settings and rates; the main currency has a row too, and a tombstone still gives old entries their look) and `txn.accountAmount` (the From/only account's side in its currency; null = `amount`). An entry stores `amount`+`currency` as entered, `amountMain`, `accountAmount` and `toAmount`; balances use `COALESCE(accountAmount, amount)` and `COALESCE(toAmount, amount)`. `domain/EntryAmounts.entryAmounts` computes them for the form, repeats and fees. A re-save keeps the stored amounts unless the amount, currency, rate, account or type changed.
    - `CurrencyRepository` publishes a `CurrencyState` (main, rows, `spec(code)`, `stripSpecs`, `fx`) and does Main Currency Setting's Data retention (`changeMainRetain`: main amounts and sub rates scaled, the old main becomes a sub), Data initialization (Backup's reset) and an account's currency change. `MoneyBookApp` copies its state into `ui/common/Currencies`, so `specOf`/`money()` recompose when a currency's look changes. The backup format is version 4: it adds the currency table and `accountAmount`.
    - M2j added budgets. The database is at version 5; `MIGRATION_4_5` creates `budget` (one row per budget and *from* month: `categoryId` null is the Total Budget, `fromMonth` is `yyyymm` or 0 for "from the start", and the deterministic id is `budget-<categoryId or total>-<fromMonth>`), and `MigrationTest` opens a version 4 file from `4.json`. `domain/Budgets` holds Realbyte's rules (the amount for a month, month and Default edits, the budget month of a Trans period: a period that starts on day 20 or later counts as its end month, `budgetLines`, `budgetYear`). `BudgetRepository` does add, edit month, edit Default, delete (tombstones) and revive in one transaction each. The backup format is version 5: it adds the budget rows. Older files restore with none. A complete reset tombstones budgets, "Reset contents only" keeps them, and Main Currency Setting's Data retention scales them.
    - M2k put the database at version 6. `MIGRATION_5_6` adds `account.state`/`account_group.state` (`ArchiveState` ACTIVE, DELETED, PURGED in `shared`) and `account.transferExpense`; `MigrationTest` opens a version 5 file from `5.json`. As in Realbyte, deleting (More → Accounts → Deleted accounts / Deleted account group restore it) and purging an account or group only set its state: the row stays live, its entries keep counting in Trans and Stats and stay editable. `accounts()`, `groups()` and `observeBalances` return only ACTIVE accounts in ACTIVE groups; importers' name lookups and the exporter see every non-tombstoned account, so a re-import never duplicates a deleted one. `AccountDetailViewModel` reads `observeAnyBalance` (read-only detail of a deleted account). `AppSettings.carryOver` and `subcategory` are synced and backed up. The backup format is version 6 (account/group state, `transferExpense`, the two settings); older files restore with the defaults.
    - M2l put the database at version 7. `MIGRATION_6_7` creates `attachment` (an entry's photos: id `<txnId>/<fileName>`, `sortOrder`, tombstones; up to 3 per entry); `TxnRow.hasPhoto` drives the list icon. Photo files live in `filesDir/photo` under `<md5 of the bytes>.jpg` names (so two entries can share one file) (`PhotoStore`, `AppContainer.photos`): `import` re-encodes anything over 2 MiB (applying EXIF orientation) and keeps smaller files as they are, so the name says `.jpg` whatever the content and readers sniff it (`ui/edit/PhotoDecode.kt` `decodePhoto`). `TxnRepository.save(txn, photos)` (null keeps, empty removes); a copy takes no photos, and two entries can name the same file. `PhotoStore.sweepUnused(db)` runs at start, after a restore and after a reset and deletes only files no live attachment names. The backup format is version 7: the zip carries the photo files beside `backup.json` (each entry capped at 16 MiB, 64 MiB free space kept; a restore stages, validates and moves them in, never deleting); older files restore with none. `AppSettings.copyDateBy` (Copy dialog: today's date or the entry's) is synced and backed up.
    - A transfer's fee is a separate expense with the id `<transferId>-fee` (note "Fees", category "Other", the From account), saved, re-saved and tombstoned with the transfer.
    - `ExportRepository` (Excel export; it writes the main amount and each account's side), `BackupRepository` (restore replaces every row and marks it dirty), `ResetRepository` (tombstones, then re-seeds the defaults over them) and `LegacyImportRepository` (skips days the existing data already covers and can keep the target account's balance unchanged).
  - **M4 change tracking** put the database at version 8 (same tables as 7; `MIGRATION_7_8` and `MoneyBookDatabase.monotonicCallback`, which `onCreate` runs and `inMemoryDb()` has too, create the `*_mono` triggers). Each trigger fires on a dirty update of a synced table and raises `updatedAt` to at least old + 1, so a local edit never goes backwards. **The DAO rule: every local write goes through the DAO `upsert`/`upsertAll`/`upsertGroups` wrappers (the DAOs are abstract classes now), which mark the row dirty (1); `applyRemote*` are clean writes for `data/sync` only.** `markAllDirty` writes `dirty = 2` so the trigger skips it (queries use `dirty != 0`). The seeds (`Seeder.seedIfEmpty(stamp)`) go in at `updatedAt` 0 on a first start, so they lose to every account row and are not marked synced-new; no currency row is seeded. Settings live in DataStore with their own `sync_updated_at`/`sync_dirty` (`SettingsRepository.syncState`, `applyRemote`, `clearDirty`); `replace` marks dirty only when a synced field changed (so Style, a device setting, doesn't). Restore tombstones every row (`softDeleteAll(now)`) and then upserts the backup at now, so it propagates as ordinary changes; a complete reset tombstones as before.
  - **`DeviceSettings` sync fields** (device-only, never backed up): `deviceId` (a random UUID made once, `deviceId()` is atomic), `serverUrl`, `refreshToken`, `syncCursor`, `syncEpoch`, `lastSyncAt`, `lastSyncError` (a `SyncError.code`). The access token lives only in memory, in `HttpSyncApi`. Logout keeps `serverUrl` for prefill. The API key is never stored (only typed once into the login form).
  - **`data/sync/`**: `SyncApi` is the transport; `HttpSyncApi` is `HttpURLConnection` with no HTTP library: login, refresh, sync, attachment HEAD/PUT/GET. A 401 refreshes once and retries, and the refresh runs under a mutex (parallel refreshes would trip the server's reuse revocation); with no token in memory the call refreshes first. `SyncError` (Offline, Unauthorized, Server, Rejected(status, error), Other) has the `code` that `lastSyncError` stores. `SyncEngine.sync()` (one run under a mutex; a caller that waited for the mutex runs its own pass; `exclusive { }` takes the same mutex, and login's token/cursor change and logout run inside it so a running sync can't push into the wrong account; signed out = `Failure(Unauthorized)` and nothing else happens) does `pass`: the dirty rows of the ten tables plus settings in batches (at most 1000 changes and 8 MiB), photos first (HEAD, then PUT only if missing, taken from the pushed attachment rows), then push/pull exchanges until `hasMore`, repeated while edits made during the run are still dirty; then downloads the missing live photos (GET to a `.part`, kept only if the MD5 equals the name; a 404 or bad file is skipped; a photo the server rejects (`Rejected`) is skipped on upload, Offline, Unauthorized and Server abort the run), then `RepeatRepository.catchUp`. The apply rule (`incomingWins`): an incoming row is written unless the local row is dirty and newer by `(updatedAt, deviceId)` with plain String compare, as on the server; after applying, `dirty` is cleared only for the exact `(id, updatedAt)` pushed, so an edit made during the request stays dirty. A changed `epoch` discards that response, `markAllDirty`, resets the cursor to 0 and runs once more. `SyncTables` maps each Room table to its DTO. `SyncAccount` does `login` (stores the tokens, probes whether the server holds data, `markAllDirty`; `NeedsChoice` when both sides have data, except when the url equals the stored one and an earlier login already synced (`lastSyncAt > 0`; logout keeps both; the key is not stored): that is the same server again, e.g. after a server restore or a key change, and it merges silently), `merge`, `replace` (the only hard delete: `wipeLocal`, cursor 0, then a full pull; seeds again if empty), `cancelLogin`, `logout`; `pending` (in memory) is true from login until it ends as Synced, so no trigger pushes before the question is answered. `SyncWorker` (CoroutineWorker; Unauthorized = signed out: cancel all and succeed), `SyncScheduler` (WorkManager 2.12.0, network-connected constraint: unique one-time `sync-start` (KEEP), `sync-soon` with a 5 s delay (APPEND_OR_REPLACE, so a request made during a run follows it), periodic `sync-periodic` every 15 minutes) and `SyncTriggers` (collects signedIn, pending and hasDirty; while signed in and not pending it enqueues periodic and start work and `soon` on every dirty change; signing out cancels all). WorkManager is touched only when signed in or on signing out. `WidgetUpdater` redraws once per `lastSyncAt` write (accepted).
  - **DI**: a hand-written `AppContainer`, owned by `MoneyBookApp` and reached from Compose with `appContainer()`. ViewModels are built with `viewModel { ... }` initializers. There is no Hilt.
  - **Domain** (`domain/`): pure functions, tested on the JVM:
    - `Periods` (month start day, week start);
    - `Formats` (Realbyte date strings, English locale);
    - `Aggregations` (day groups, calendar grid of 42 cells, monthly rows with week rows, accounts overview with each card's `CardStatus`). `totalsOf`, `groupByDay`, `buildCalendar`, `buildMonthly` and `widgetSummary` take a `CardExpenseMode`: in Lump sum (B), `TxnRow.countedAs` leaves card expenses out and counts transfers into a card as expenses (Trans and the summary widget only; Stats and account detail keep A). `countedAs` also applies Transfer-Expense: a transfer into a flagged account from an unflagged one counts as an expense, the reverse as income; every income/expense sum (budgets, Search totals, the widget) goes through it, and Stats gives such transfers one slice per account group (`GROUP_SLICE`);
    - `CarryOver` (`carryOver`, `withCarryOver`): Carry-over Setting's synthetic "Carry-over" row on the period's first day (last in Daily, first in Calendar), not stored, only in Daily/Calendar and only without a Trans filter (`TransViewModel.carryOverFlow`);
    - `AmountInput` (keypad state);
    - `StatsPeriod` (a week, month, year or custom range: its date range, stepping, titles and route encoding);
    - `Stats` (category slices with subcategories rolled into their parent, trend sums per period, the Trans → Total breakdown);
    - `TxnFilter` and `filterOptions` (the Trans filter: ticked top-level categories and accounts, and the panel's lists);
    - `Search` (`SearchFilter`, `search`, `searchTotals`, `rankSuggestions`). Matching runs in Kotlin over `TxnRepository.observeAll()`, because SQLite's `LIKE` folds case only for ASCII ("JÍDLO" must find "jídlo").
    - `RepeatSchedule` (occurrence dates per frequency; monthly dates are counted from the start, so day 31 survives short months) and `splitInstallments` (the first part takes the remainder);
    - `Calculator` (the keypad's calculator: × and ÷ before + and −, results rounded half-up to the currency).
    - `WidgetSummary` (`momRanges`, `mom`, `widgetSummary`): the summary widget's This Month (the whole month under the Monthly Start Date) and vs. MoM (the month so far against the same number of days from the previous month's start, the percent is of last month, half up, and none when last month was 0).
    - `CardStatement` (Money Manager's card rules): a period starts on the settlement day S (the month's last day when shorter) and ends the day before the next start; account detail's month M shows the period that ends in M; the payment date is the first day P after the period's end. `status(balance, charges, today, S, P)` gives `CardStatus(payable, outstanding, overdue)`: Outst. = min(owed, this period's charges), Payable = the rest, overdue = what payments have not covered from periods whose payment date has come (payments go to the oldest debt); `payPrefill` is overdue, else Payable.

## Project rules

- Never commit personal financial data. `reference/` (local captures and decompiled sources, never published) and root-level `*.xls`/`*.xlsx`/`*.zip` are gitignored for that reason. Test fixtures are synthetic.
- Money is always `Long` minor units plus a currency code.
- Features not built yet must not appear as dead buttons; each is added in the milestone that implements it. The remaining settings screens are later M2 parts. Online exchange rates (Realbyte's refresh buttons) and user-defined currencies are not built.
- `.env`, `deploy/.env` and `deploy/backups/` hold secrets and financial data and are gitignored; acceptance runs use a throwaway env file outside the repo.
- Work directly on `main`; no feature branches.
